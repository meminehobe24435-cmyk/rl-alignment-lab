# rl-alignment-lab

**不依赖任何深度学习 / 强化学习框架，用 numpy 手写前向与反向传播，从零实现 PPO 与 GRPO，在一个「可验证奖励」的代码修复任务上跑通完整的 RL 训练闭环。**

核心训练与评估链路**只依赖 `numpy` + Python 标准库**：没有 torch、没有 jax、没有 gym、没有 trl、没有 ray。
线性层、单头点积注意力、softmax、交叉熵、ReLU/tanh、Adam/SGD 的**反向传播全部手推**，
并用**中心差分数值梯度**逐参数校验（实测最大相对误差 `4.5e-07`）。

---

## ⚠️ 先说清楚这是什么

**这是一个把 RL 算法原理"拆到能自己写出来"的教学/练手工程，不是大模型训练项目。**

- 策略网络是**手写的小网络**：参数量 `41,590`（策略）+ `4,929`（Critic），
  跟"大模型 RL 训练"差若干个数量级；
- 任务是**自造的迷你表达式语言**，不是 SWE-bench 之类的真实代码修复数据集；
- 奖励是**规则可验证**的（跑测试用例），**没有**偏好数据、**没有**学出来的 reward model；
- 单机 CPU、无分布式、无训推分离、没做过吞吐与稳定性优化；
- 全文所有数字都来自**本仓库代码的真实运行**，没有一个是编的。
  连"RL 没能赢过基线"这种情况也照实写（见下方结果）。

**它值钱的地方在于**：PPO 的 GAE 与裁剪目标、GRPO 的组内归一化、KL 惩罚的两种写法、
优势归一化、熵塌缩、cold-start 失败——这些细节我是真的自己踩了一遍，
而不是调库调出来的。

---

## 为什么做这个

> 想真的搞懂 PPO / GRPO 的**实现细节**，而不是调库。

用 `stable-baselines3` 或 `trl` 跑通一个 RLHF 脚本只要几十行，但那些行里藏着的东西全都被封装掉了：
advantage 到底是逐 token 还是逐序列？KL 是放进奖励还是放进损失？组内归一化的 `std=0` 怎么处理？
裁剪之后的梯度到底是不是 0？熵正则的系数大一点会发生什么？

这些东西**只有自己把反传写一遍才真的清楚**。所以我连 autograd 都自己写：
每个 `backward` 方法里的矩阵乘法就是链式法则展开后的结果，没有计算图引擎兜底。
写完之后的直接好处是：**梯度对不对是可以被机器证明的**（有限差分），
而不是"loss 降下去了所以应该没错"。

顺带一个工程上的好处：零依赖让 CI 又快又稳（不需要下载几百 MB 的 wheel），
四平台矩阵（Ubuntu/Windows × Python 3.10/3.12）几十秒就能跑完。

## 关键结果

### 1. 四基线对比（固定评测集，200 个任务，与训练集**互不相交**）

评测集只在评估时使用；所有方法共用同一套任务划分、同一个评测种子、同一套奖励。
成功率是采样解码（temperature=1）的结果，`±1SE` 是二项标准误 `√(p(1−p)/n)`。

**种子 0（默认配置）：**

| 方法 | 成功率(采样) | ±1SE | 成功率(贪心) | 平均 reward | 结果奖励 | 过程奖励 | 截断率 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `random` 随机策略 | 0.0% | ±0.0% | — | 0.0246 | 0.0000 | 0.0821 | 53.0% |
| `sft` 行为克隆 | 16.5% | ±2.6% | 19.0% | 0.4670 | 0.1925 | 0.9149 | 0.0% |
| `ppo` 从头训练 | 0.0% | ±0.0% | 0.0% | 0.2113 | 0.0000 | 0.7045 | **100.0%** |
| `grpo` 从头训练 | 0.0% | ±0.0% | 0.0% | 0.2103 | 0.0138 | 0.6551 | 1.5% |
| `ppo_sft_init`（SFT 权重起步） | **24.0%** | ±3.0% | 26.5% | 0.5477 | 0.2712 | 0.9214 | 0.0% |
| `grpo_sft_init`（SFT 权重起步） | **26.5%** | ±3.1% | 27.0% | 0.5685 | 0.2900 | 0.9284 | 0.0% |
| `ppo_outcome_only`（消融：只用结果奖励） | 0.0% | ±0.0% | 0.0% | 0.0000 | 0.0000 | 0.6971 | **100.0%** |

**三个种子的横向验证**（同一套配置，只换 `--seed`）：

| 方法 | seed=0 | seed=1 | seed=2 | 均值 |
| --- | ---: | ---: | ---: | ---: |
| `random` | 0.0% | 0.0% | 0.0% | 0.0% |
| `sft` | 16.5% | 18.0% | 17.5% | 17.3% |
| `ppo`（从头） | 0.0% | 0.0% | 0.0% | 0.0% |
| `grpo`（从头） | 0.0% | 0.0% | 0.0% | 0.0% |
| `ppo_sft_init` | 24.0% | 19.0% | 20.0% | **21.0%** |
| `grpo_sft_init` | 26.5% | 21.0% | 21.0% | **22.8%** |
| `ppo_outcome_only` | 0.0% | 0.0% | 0.0% | 0.0% |

### 2. 结论（含"RL 没赢"的诚实部分）

1. **RL 从零开始训练完全失败（0.0%，三个种子一致）。**
   在"只有句末一次可验证奖励"的稀疏奖励任务上，随机初始化的策略几乎不可能采样到
   任何正确答案，结果奖励恒为 0、梯度恒为 0 —— 典型的 **cold-start** 问题。

2. **RL 从 SFT 权重出发，稳定超过 SFT 基线。**
   三个种子上 `grpo_sft_init` 相对 `sft` 提升 **+10.0 / +3.0 / +3.5 个百分点**（均值 +5.5pp），
   `ppo_sft_init` 提升 **+7.5 / +1.0 / +2.5 个百分点**（均值 +3.7pp）。
   提升方向和幅度在三个种子上一致，但**单次运行的差距（1~5 个任务）落在 ±1SE(≈3pp) 附近，
   严格说只有 seed 0 的 GRPO 提升（+10.0pp）超出了 2 个标准误**。我不打算把它讲成"显著胜出"。

3. **RL 用的是比 SFT 更弱的监督。**
   SFT 拿到的是 1000 条专家轨迹（逐 token 的正确答案），
   RL 只拿到 1000 条提示和一句标量奖励 —— 在同一份数据上，RL 用更弱的信息达到了更高的成功率。
   这才是这个对比真正的意义所在。

4. **纯结果奖励下 RL 完全学不动（消融）。** 把过程奖励权重设为 0，
   PPO 训练 80 次迭代后平均 reward 精确等于 `0.0000`，成功率 `0.0%`，截断率 `100%`。
   过程奖励在本项目里不是"锦上添花"，而是**能不能起步的前提**（详见下文）。

5. **GRPO 比 PPO 更稳。** 同样的数据与步数，GRPO 不需要 Critic、
   组内归一化天然把奖励尺度抹平，最终成功率和"训练集成功率保持度"都更好；
   PPO 的 Critic 在策略快速变化时会出现价值损失飙升（见踩坑记录第 2 条）。

### 4. 失败模式分类

桶是互斥的，按优先级判定：`ok` → `truncated` → `unbalanced_paren` → `syntax` → `eval_error` → `semantic`。

**seed 0，200 个评测任务的分类结果：**

| 方法 | `ok` | `truncated` | `unbalanced_paren` | `syntax` | `eval_error` | `semantic` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `random` | 0.0% | 53.0% | 20.5% | 20.5% | 0.0% | 6.0% |
| `sft` | 16.5% | 0.0% | 3.5% | 0.0% | 0.5% | **79.5%** |
| `ppo`（从头） | 0.0% | **100.0%** | 0.0% | 0.0% | 0.0% | 0.0% |
| `grpo`（从头） | 0.0% | 1.5% | 1.0% | 6.0% | 0.0% | **91.5%** |
| `ppo_sft_init` | 24.0% | 0.0% | 3.5% | 0.0% | 0.0% | 72.5% |
| `grpo_sft_init` | 26.5% | 0.0% | 2.5% | 0.5% | 0.0% | 70.5% |
| `ppo_outcome_only` | 0.0% | **100.0%** | 0.0% | 0.0% | 0.0% | 0.0% |

**怎么读这张表：**

- 训练过的模型基本不犯**低级错**了：`syntax` / `unbalanced_paren` / `eval_error` 加起来不到 3.5%。
  语法层面的东西是最容易学的。
- **剩下的错误几乎全是 `semantic`（≈70–80%）**：模型写出的表达式语法完全合法、
  能算、不除零，但**算出来是错的**。这是真正的瓶颈 —— 模型没有学会"数值上正确的修复"，
  而是学会了"生成一个看起来很像的表达式"。
- `random` 的 53% 截断率来自它在 14 步预算内很少碰巧采样到 `<eos>`。
- **纯结果奖励 / RL 从头的 100% 截断率非常有信息量**：策略发现"根本不输出 `<eos>`"
  可以让 episode 不结束、也就永远拿不到那个残酷的 0 分奖励 —— 这是稀疏奖励下
  一种典型的退化行为，值得单独记录。

`semantic` 桶里的典型例子（`grpo_sft_init`，全部来自真实运行记录）：

| 任务 | 带 bug 输入 | 目标 | 模型输出 | 通过用例 |
| --- | --- | --- | --- | --- |
| ev-000 | `b*a-(2-8)` | `b*a-(2-2)` | `b*a-(2-8)` | 0/4 |
| ev-001 | `1+1-b-c` | `3+1-b-c` | `1+1-b-c` | 0/4 |
| ev-002 | `b/1/2` | `a/1/2` | `b/1/2` | 0/4 |

三行都是同一个失败形态：**模型直接原样输出了带 bug 的表达式**。
因为"抄输入"在过程奖励（编辑相似度）下得分很高，而在结果奖励下拿 0 ——
它卡在了这个局部最优里。

失败样本的**平均用例通过比例只有 0.034**，也就是说失败不是"差一点点"，
而是"基本没修对"。

**按注入 bug 类型看成功率**（`grpo_sft_init`，200 个评测任务），
这张表解释了瓶颈到底在哪里：

| 注入的 bug | 样本数 | 成功率 | 这类 bug 长什么样 |
| --- | ---: | ---: | --- |
| `dup_op` 复制一个运算符 | 33 | **63.6%** | 带 bug 输入本身是**语法错误**（如 `a++b`） |
| `insert_op` 插入一个运算符 | 33 | **51.5%** | 同上，多了一个运算符 |
| `drop_paren` 删掉一个左括号 | 20 | **35.0%** | 括号明显不配平，结构性错误 |
| `delete_char` 删掉一个字符 | 24 | 8.3% | 缺个操作数 |
| `swap_digit` 改一个数字 | 42 | **7.1%** | 语法完全合法，只是数值错 |
| `swap_var` 换一个变量 | 28 | **7.1%** | 语法完全合法，只是数值错 |
| `swap_op` 换一个运算符 | 20 | **5.0%** | 语法完全合法，只是数值错 |

**规律很清楚**：**能不能用"看"发现错误，决定了修得对不对。**

- 前三类（`dup_op` / `insert_op` / `drop_paren`）的带 bug 输入**本身就是非法表达式**，
  模型只要学会"生成合法表达式"就能顺手修掉，成功率 35%–64%；
- 后四类（`swap_*` / `delete_char`）**语法完全合法**，
  必须真的理解"这个表达式在给定变量下算出来不对"才能修，
  成功率掉到 5%–8%。

这与前面"失败几乎全是 `semantic`"的观察是同一件事的两面：
**模型学会了语法，没学会语义。** 在只有 4.2 万参数、1000 条训练样本的设定下，
要它从标量奖励里反推出"数值语义"这个能力，难度远超"生成合法符号串"。

## 已实现的范围（分模块）

```
rlalign/
├── nn.py         手写层与优化器：Linear、Embedding、SingleHeadAttention、
│                 ReLU/tanh 及其导数、数值稳定 softmax/log-softmax、
│                 softmax 熵、SGD(momentum)、Adam、全局梯度范数裁剪
├── env.py        迷你表达式语言：词法/语法（递归下降）/精确有理数求值器、
│                 可验证测试框架、任务集生成（7 种 bug 注入）、train/eval 划分
├── policy.py     自回归策略网络：提示编码器 + 单头点积注意力 + 单隐层 MLP 解码器，
│                 手推前向与反向；Critic（价值网络）；参考策略快照
├── reward.py     可验证结果奖励（通过用例比例）+ 过程奖励（语法/可求值/编辑相似度）
├── rollout.py    轨迹采样：单样本（PPO）与组采样（GRPO），含填充与掩码
├── ppo.py        GAE(λ)、优势归一化、clipped surrogate、价值损失、熵正则、KL 惩罚
├── grpo.py       组内归一化优势（含退化处理）、无 Critic、KL 直接进损失
├── train.py      训练闭环：随机基线、行为克隆 SFT、PPO/GRPO 主循环
├── eval.py       固定评测集评估（采样 + 贪心），二项标准误
├── failure.py    失败模式分类（6 个互斥桶）+ 典型例子 + 按注入 bug 类型统计
├── gradcheck.py  有限差分数值梯度校验（中心差分，两条判据）
├── artifacts.py  确定性 JSON/JSONL 落盘 + 参数检查点
├── plots.py      训练曲线与对比图（matplotlib 惰性导入，缺失时优雅降级）
└── cli.py        all / train / baseline / eval / failure / report / gradcheck
tools/
├── check_reproducibility.py   同命令跑两次，指标文件逐字节比较
└── check_zero_deps.py         静态+运行时双重零依赖守卫
```

**技术要点：**

- **PPO**：GAE(λ) 优势估计（支持掩码、终止步不 bootstrap）、clipped surrogate
  （逐 token 比值裁剪）、**Critic 价值网络** + 价值损失、熵正则、优势归一化、
  对参考策略的 KL 惩罚（k1 塑形进奖励 + k3 无偏估计做监控）。
- **GRPO**：同一提示采一组（G=8）轨迹、**组内归一化优势** `(R−μ)/(σ+ε)`、
  **不需要 Critic**、KL 以 k3 形式直接进损失。
- **手写反向传播**：所有层的前向与反向都是手推公式，**没有任何 autograd**。
- **可验证奖励**：`reward = 通过测试用例数 / 总用例数`，用 `fractions.Fraction`
  做**精确有理数**比较 —— 没有浮点容差，不匹配就是不匹配。

### 网络结构与规模

| 组件 | 结构 | 参数量 |
| --- | --- | ---: |
| 提示编码器 | `(P·d) -> d` 线性 + tanh，P=16, d=32 | 16,416 |
| 注意力记忆 | 单头点积注意力 `K=W_k E`、`V=W_v E+b_v`，`d_k=d_v=32` | 5,152 |
| 解码器 | `[h0; e_prev; pos_t; ctx] -> 128 -> ReLU -> 22` | 20,022 |
| 嵌入表 | token(22×32) + 提示位置(16×32) + 生成位置(14×32) | 1,664 |
| **策略合计** | | **41,590** |
| Critic | `[h0; e_prev] -> 64 -> ReLU -> 1`（独立嵌入表） | 4,929 |

词表只有 **22 个 token**（`<pad> <bos> <eos>` + `0-9` + `+-*/()` + `a b c`）。

## 超参与为什么这么选

### PPO（`rlalign/ppo.py::PPOConfig`）

| 超参 | 取值 | 为什么 |
| --- | ---: | --- |
| `clip_eps` ε | 0.2 | PPO 原论文默认值，也是 RLHF 的事实标准；本项目没发现需要改的理由 |
| `kl_coef` β | 0.05 | 逐 token 的 k1 塑形系数。β=0.02 时 SFT→RL 会把策略推漂（KL 涨到 1.9 nat/token、成功率反而掉）；β=0.2 以上又会把 RL 锁死在 SFT 附近学不动。0.05 让 KL(k3) 全程稳定在 0.02 以内 |
| `lr` | 3e-4 | **最关键的一个数**。3e-3 下策略 10 次迭代内被彻底摧毁（详见踩坑第 2 条）。3e-4 时 ratio 全程 ≈1.00、clip_frac<1% |
| `gamma` γ | 1.0 | 任务是有限步的、且奖励只在终止步给一次；折扣只会无谓地削弱远端信号 |
| `lam` λ | 0.95 | GAE 的标准取值。任务里"过程奖励"是逐 token 的稠密信号，λ 太小会让它传不回早期 token |
| `ent_coef` | 0.02 | 防熵塌缩。SFT 后的策略熵本来就只有 ≈0.1，再不护着就变成确定性输出、RL 失去探索能力 |
| `vf_coef` | 0.5 | 价值损失权重，PPO 常用默认值 |
| `max_grad_norm` | 1.0 | 全局 L2 裁剪，防止偶发的大梯度把策略打飞 |
| `inner_epochs` | 2 | 每批 rollout 复用 2 次。再多会让 off-policy 偏移变大（ratio 越界率上升） |
| `prompts_per_iter` | 32 | 每次迭代采 32 条提示（各 1 条轨迹）。CPU 预算下"看到足够多样的提示"比"每条提示多采几条"更重要 |
| `iterations` | 80 | 实测 40 次左右就收敛，80 次留出观察空间，总时长仍在预算内 |

### GRPO（`rlalign/grpo.py::GRPOConfig`）

| 超参 | 取值 | 为什么 |
| --- | ---: | --- |
| `group_size` G | 8 | 组内归一化要估计均值和方差，G 太小估计噪声大；G=6 与 G=8 的最终成功率差异落在噪声内，选 8 保险一些 |
| `lr` | 3e-4 | 与 PPO 保持一致，便于对比 |
| `kl_coef` β | 0.05 | 与 PPO 同值，保证两个算法**只差在"critic vs 组内归一化"这一点上**，对比才干净 |
| `clip_eps` ε | 0.2 | GRPO 沿用了 PPO 的裁剪目标，ε 同值 |
| `ent_coef` | 0.02 | 同 PPO |
| `prompts_per_iter` | 12 | 每次迭代 12 条提示 × 8 条 = 96 条轨迹/迭代，与 PPO 的单次采样量级相当 |
| `eps_std` | 1e-4 | 组内标准差的数值保护，也是 DeepSeekMath 的取值 |
| `iterations` | 80 | 与 PPO 相同 |

**说明：GRPO 没有 `gamma` / `lam` / `vf_coef`，因为没有 Critic、也不做 GAE** ——
优势是序列级标量、直接广播到该轨迹的每个 token。在"只在句末给一次奖励"的任务上，
不做逐 token 信用分配反而更合适。

超参是怎么定的：先用 **120 个任务的训练集**做小规模扫描，
再用一个**独立的验证集**（`generate_tasks(60, seed=777001)`，与评测集不同）选参，
最后才在评测集上跑一遍报告结果。扫描过程中发现"数据量不够导致泛化恒为 0"，
于是把训练集从 120 扩到 1000（见踩坑第 4 条）。

## 开发过程中被测试抓出来的真问题

以下每一条都是真实发生过的，且都是**被测试或校验脚本抓出来**的，不是我事后编的。

### 1. 层内部缓存被下一步覆盖 → 整条序列的反传全错（相对误差 = 1.0）

**现象**：第一次跑 `rlalign.cli gradcheck`，策略网络的**最大相对误差是 1.0**，
也就是解析梯度和数值梯度**完全对不上**。Critic 也是 1.0。

**原因**：`Linear.forward` 把输入存进 `self._x`，`backward` 再从 `self._x` 取。
在逐步解码的序列循环里，每一步的 `forward` 都会覆盖 `self._x`，
于是整条序列反传时**每一步用的都是最后一步的激活值**。
同一轮里还发现了第二个 bug：`step_backward` 忘了把 `dx` 的后两段
（上一 token 的嵌入、生成位置嵌入）scatter-add 回嵌入表 —— 输入嵌入的梯度被整个丢掉了。

**修法**：把 `Linear.backward(dy, x)` 改成**必须显式传入 x**，
并且把反传需要的一切（`x, a1, h1, prev_id, t`）全部打进 cache 元组。
修完后相对误差降到 `8.4e-09`。

**为什么值得记**：这类 bug 在"loss 在降"的时候完全看不出来 ——
它只是让梯度变慢、变歪，而不是变 NaN。**只有数值梯度校验能抓住它。**

### 2. 学习率 3e-3 把策略彻底摧毁（KL 涨到 8+，价值损失涨到 27）

**现象**：`lr=3e-3`，从 SFT 权重出发跑 PPO，
**训练集成功率 10 次迭代内从 1.00 掉到 0.00**，KL(k3) 从 0.05 涨到 8.3，
Critic 的价值损失从 0.63 涨到 27.6。而同一份代码换成 `lr=3e-4` 就完全稳定。

更反直觉的是：**把 `kl_coef` 从 0.02 加到 0.2，KL 反而涨得更凶（1.9 → 13.7）**。
原因有两层：一是 KL 惩罚被放进奖励后，**优势归一化会把它的常数部分直接消掉**，
所以加大 β 并不能阻止漂移；二是 lr 过大时每一步都跨过了信任域，
比值 `exp(logπ_new − logπ_old)` 反复越界，裁剪之后梯度为 0，
策略只能被熵正则和 Critic 的噪声推着乱走。

**修法**：`lr` 从 3e-3 降到 3e-4（这条是扫描验证过的），
`kl_coef` 定在 0.05，同时监控 `clip_frac` 和 `ratio_mean` 作为"是否跨出信任域"的报警器。

### 3. GRPO 组内奖励全相等时除零 / 布尔掩码维度不匹配

**现象**：跑 GRPO 时先是 `IndexError: boolean index did not match indexed array`，
改完之后理论上的 `std=0` 分支又可能产生 NaN。

**原因**：`std` 的形状是 `(n_groups, 1)`，
用它去布尔索引 `(n_groups, group_size)` 的数组时广播规则不成立。
更深一层的问题是：组内奖励全相等时分子恒为 0、分母也恒为 0，
即使侥幸不报错，`0/0` 也会把 NaN 灌进梯度。

**修法**：改成 `scale = np.where(std >= eps, 1.0/(std+eps), 0.0)`，
用 `np.where` 广播而不是布尔索引，std 小于阈值时**把整组的优势显式置 0**
（而不是让数值自己碰运气）。单测里专门覆盖了"整组退化"和"只有某组退化"两种情况。

### 4. 数据量不够时泛化恒为 0，RL 无处可学

**现象**：一开始用 120 个训练任务，SFT 在**训练集上能到 99.2%**，
但在评测集上**恒为 0.0%**（换过 3 个种子）。RL 更惨：从 SFT 出发后
训练集成功率反而从 0.99 掉到 0.29。

**原因**：120 条样本配 4 万参数，模型把 (提示 → 目标) 整个背下来了，
完全没有学到"改一个字符"这个操作。RL 也没有任何可优化的空间 ——
训练集已经被 SFT 做到 99%，advantage 几乎全为 0，剩下的只有噪声。

**修法**：把训练集扩到 **1000**，SFT 的评测集成功率立刻从 0% 涨到 **16.5%**
（进一步扩到 1200 时是 25%）。**瓶颈是数据，不是算法。**

### 5. 提示编码太弱，解码器根本"看不到"输入的 bug

**现象**：第一版用 `h0 = mean(提示的逐位置嵌入)`。
SFT 训练集成功率 86.7%，评测集 0%。把训练集扩到 1000 也救不回来。

**原因**：mean-pool 是个严重的信息瓶颈 —— 16 个位置的嵌入被平均成一个 32 维向量，
"第 4 个字符是 `*` 还是 `+`"这种信息基本被抹平了。
换个更强的编码器（`tanh(W·flatten(E))`）后训练集能到 99.2%，但评测集**仍然是 0%**，
因为解码器每一步都只能看到那个固定的 `h0`，**没有任何机制在当前位置回头看提示**，
学不会"复制 + 局部改写"。

**修法**：给解码器加上**对提示的单头点积注意力** ——
每一步用 `[h0; pos_gen[t]]` 作为 query，对提示的逐位置嵌入做 softmax 加权。
加上之后评测集成功率从 0% 变成 3.3%（120 任务）/ 16.5%（1000 任务），
失败模式也从"输出乱七八糟"变成了**"原样抄输入"**（这才是可修的方向）。

### 6. 注意力里有个数学上梯度恒为 0 的废参数

**现象**：把注意力加进去之后梯度校验又红了：`bk[14]` 的解析梯度是 `-0.0`、
数值梯度是 `1e-10`，**相对误差 1.0**。

**原因**：这不是反传错了，而是 `bk` 本身是个废参数 ——
给 K 加一个常数偏置会让注意力分数多出一个与位置无关的常数项，
而 **softmax 对常数平移不变**，所以 `∂L/∂bk ≡ 0`。
数值梯度里那 `1e-10` 纯粹是 `L` 的浮点舍入噪声除以 `2ε` 得到的。

**修法**：两件事一起做 ——
(a) **把 `bk` 直接删掉**（数学上冗余的参数不该留在代码里）；
(b) 把校验判据改成**两条**：梯度幅度 ≥1e-4 的分量用相对误差（<1e-5），
更小的分量用绝对误差（<1e-8，仍比真实 bug 小 4~5 个数量级）。
理由是中心差分的绝对噪声下限约为 `δ|L|/ε ≈ 1e-10`，
用相对误差去卡一个 `1e-6` 量级的梯度只会量到噪声。
单测里专门加了一条 `test_attention_k_has_no_bias` 把这个设计决定钉住。

### 7. 快照用参数名做键，三个嵌入表互相覆盖

**现象**：第一次跑测试时 `load_snapshot(ref, snapshot(pol))` 直接抛
"快照与模块的参数结构不一致"。

**原因**：`snapshot` 用 `{name: array}` 存参数，而策略里**三个嵌入层的参数名都叫 `E`**
（token 嵌入、提示位置嵌入、生成位置嵌入），字典把后两个覆盖掉了 ——
7 个参数张量最后只剩 3 个键。
如果没被长度检查拦住，参考策略会被**悄无声息地污染**，KL 惩罚直接算错。

**修法**：`snapshot` / `load_snapshot` 改成**按位置**索引的列表，
并加了长度与形状校验。单测 `test_snapshot_handles_duplicate_parameter_names`
把它钉死。

### 8. Windows 控制台 GBK 编码让 CLI 直接崩

**现象**：`rl` 命令打印带 `✓` 的中文日志时抛 `UnicodeEncodeError: 'gbk' codec can't encode`。

**修法**：`main()` 里把 `sys.stdout/stderr` 显式 `reconfigure(encoding="utf-8")`，
并把非 ASCII 的装饰符号换成 `PASS` / `FAIL`，保证跨平台一致。

### 9. NaN 会静默传播

**现象**：写 `test_softmax_rejects_non_finite` 时发现，
把 `NaN` 喂进 `softmax` 会一路算出 NaN 而不报错。

**修法**：`softmax` / `log_softmax` 在入口做 `np.isfinite` 检查并直接抛 `ValueError`。
NaN 在训练循环里通常要过几个 epoch 才表现为"loss 突然变成 nan"，
在源头拦住比事后排查便宜得多。

### 10. `addopts` 里的 `-q` 加上命令行的 `-q` = `-qq`，把测试数量吞掉了

**现象**：本地和 CI 的 pytest 输出都只有进度点，**没有 "N passed in Xs" 这一行**，
翻 CI 日志时无法直接确认到底跑了多少用例（只能去数点）。

**原因**：`pyproject.toml` 里写了 `addopts = "-q"`，而调用时又传了一次 `-q`，
pytest 的 `-q` 是可叠加的，两次叠加变成 `-qq` —— 额外一级安静会**连汇总行一起省略**。

**修法**：从 `addopts` 里去掉 `-q`（换成 `--strict-markers --strict-config`），
`-q` 只由调用方传一次。现在输出稳定带汇总行：`230 passed in 16.21s`。

**为什么值得记**：它不影响正确性，但它**破坏了"证据的可核查性"** ——
CI 明明是绿的，日志里却找不到测试数量。这类问题只有真的去翻日志才会发现。

## 边界与已知限制

1. **这不是大模型。** 策略网络是手写的小网络（策略 `41,590` 参数 + Critic `4,929` 参数），
   跟"大模型 RL 训练"差若干个数量级。它是一个条件语言模型，但词表只有 22 个 token、
   序列不超过 14 步。
2. **单机 CPU、零依赖、无分布式、无训推分离。** 没有做过吞吐与稳定性优化，
   也没跑过多机多卡。整个闭环一条命令 94 秒，完全按单核 CPU 设计。
3. **任务是自造的迷你语言。** 四则运算 + 变量 + 括号，不是 SWE-bench 之类的真实代码修复数据集。
   "可验证奖励"（奖励来自执行测试而不是人打分）这个思路是真的，
   但场景是玩具级的，自动化 bug 注入也不是真实缺陷分布。
4. **没有用真实大模型做 RLHF / RLVR**，没有偏好数据，没有学出来的 reward model。
   奖励规则完全可验证（跑测试用例），因此**也不涉及 reward hacking 的对抗性研究** ——
   虽然本项目确实观察到了"不输出 `<eos>` 以逃避 0 分"这种对奖励结构的退化利用。
5. **未使用也未实现 Ray / DeepSpeed / Megatron-LM / vLLM 等训练框架**，
   没有并行策略、没有 ZeRO、没有 KV cache、没有 PagedAttention、没有连续批处理。
6. **结论的统计强度有限。** 评测集 200 个任务，±1SE ≈ 3 个百分点；
   种子间波动也在同一量级。因此"RL 超过 SFT"这个结论我按三个种子如实列出，
   并明确指出只有 seed 0 的 GRPO 提升超出了 2 个标准误。
7. **超参只在 1 个训练集规模 + 1 个验证集上扫过**，没有做大规模的鲁棒性研究。

## 测试与 CI

### 单元测试：230 项

```bash
python -m pytest -q          # 本地 230 passed in 16.21s
```

覆盖的重点（按重要性排序）：

1. **数值梯度校验**（13 项）：对策略网络与 Critic 的**每个参数张量**抽样做中心差分比对。
   用两个不同量级的判据（相对误差 / 绝对误差），并验证"扰动后参数被恢复原样"、
   "每个参数张量都被覆盖到"、"换种子依然通过"。
2. **求值器与测试框架**（46 项）：运算符优先级、左结合性、精确有理数除法、
   多位数与前导零、**非法输入边界**（空表达式、一元负号、孤立运算符、
   括号不配平、双运算符、除零、未绑定/非法变量）。
3. **奖励函数**（23 项）：全对 → 1.0、全错 → 0、部分对 → 精确比例
   （手工构造任务验证 0.5 / 0.25 / 0.0 三档）、过程奖励各分量。
4. **GAE 与手算一致**（5 项）：构造 3 步和 4 步的小例子，期望值**算好写死在断言里**，
   另外覆盖 λ=0 退化为 TD 误差、λ=γ=1 退化为 MC−V、终止步不 bootstrap、掩码传播。
5. **GRPO 组内归一化**（6 项）：均值 ≈0、标准差 ≈1；**退化输入**（组内全相等 → 优势全 0，无 NaN）；
   只有某组退化；scale/shift 近似不变性。
6. **PPO clip 边界**（5 项）：比值超出 `[1−ε, 1+ε]` 后**目标函数不再变化**（数值上完全相等），
   越界处梯度严格为 0，域内梯度为 `−A`。
7. **KL 估计**（2 项）：策略与参考策略相同时 k1 与 k3 均 ≈ 0；k3 恒非负。
8. **softmax 数值稳定性**（8 项）：大 logits 不溢出、平移不变、极负 logits 不 NaN、
   NaN/Inf 输入直接报错。
9. **优化器**（7 项）：SGD/Adam 单步更新方向沿负梯度、动量累积、
   Adam 的第一步约为 `lr`、Adam 对梯度尺度近似不变、梯度裁剪。
10. **训练真的能提升成功率**（4 项）：小规模 SFT 训练，断言训练集成功率
    从随机水平（<5%）提升到 >50%，且 loss 单调下降、过程奖励上升。
11. **确定性**：同种子两次 rollout 完全一致、SFT 权重逐元素一致、
    随机策略基线可复现、贪心解码可复现。
12. **CLI 入口**（15 项）：所有子命令、缺文件时的退出码、`all` 端到端产物完整性、
    消融配置确实把过程奖励权重设为 0。

```
  ✓ summary_ppo.json   sha256=e993fa66b7f924d3...
...
结论：全部逐字节一致 ✓（比较了 8 个文件）
```

**更强的一个事实**：这 8 个文件的 SHA-256 在
**Ubuntu / Windows × Python 3.10 / 3.12 四个平台上完全相同**
（例如 `failure_ppo.json` 恒为 `c80ecf211ac6c5c4...`）。
也就是说不仅"同机跑两次一致"，而是**跨操作系统、跨 Python 版本都逐字节一致**。

做到逐字节一致靠三件事：
(1) 全部随机性来自写死种子的 `np.random.default_rng`；
(2) `rlalign/__init__.py` 在导入 numpy **之前**把 BLAS/OMP 线程数钉成 1，
避免多线程归约顺序不同导致 float64 末位漂移；
(3) 上报浮点数统一 round 到 6 位小数、JSON 排序键、统一 LF 换行
（Windows 上显式用 `newline="\n"`，否则会写出 `\r\n` 导致跨平台不一致）。

### 零依赖守卫

```bash
python tools/check_zero_deps.py
```

静态扫描 `rlalign/` 的 AST 找出所有 import，再真实导入全部子模块检查 `sys.modules`，
双重确认没有 `torch` / `tensorflow` / `jax` / `gym` / `ray` / `trl` /
`stable-baselines3` / `tianshou` / `transformers` / `scipy` / `pandas` / `sklearn` 等模块混进来。
`matplotlib` 作为**可选**依赖单独列出（只在画图分支惰性导入，缺失时优雅降级）。
